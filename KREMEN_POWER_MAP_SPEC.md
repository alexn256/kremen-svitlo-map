# Карта отключений света — Кременчук

## Контекст

Телеграм-бот "Svitlo Kremen Bot" (отдельный проект, см. `mazambik_parser_bot`) в
реальном времени знает статус 12 подочередей Кременчука (1.1–6.2): включена,
выключена, или идёт переключение — он получает это с сайта poe.pl.ua.

Есть справочник "адрес → подочередь" (PDF-график Полтаваобленерго), из которого
вручную готовится список домов Кременчука с привязкой к конкретной подочереди.
Важно: на одной и той же улице соседние дома могут относиться к *разным*
подочередям — это подтверждено вручную, не баг исходных данных.

Цель: отдельный сайт с картой Кременчука, на которой каждый дом из списка
окрашен в цвет своей текущей подочереди (зелёный — есть свет, красный — нет,
жёлтый — переключение), и эта раскраска обновляется вслед за live-статусом
бота.

**Это отдельный проект**, не часть репозитория бота. Парсинг исходного PDF и
подготовка списка адресов делается вручную/отдельно и в это ТЗ не входит —
сюда входит всё начиная с готового списка адресов.

## Как это должно выглядеть

Не плоская карта с маркерами-пинами, а наклонная (как в играх) 3D-карта:
нейтральный серый городской фон (улицы, парки, подписи), и поверх него —
подсветка конкретных домов из нашего списка объёмными цветными полигонами
(сами здания меняют цвет, а не иконка/пин над ними светится). По сути —
"маска поверх карты", где подсвечена только наша выборка домов, весь
остальной город остаётся нейтральным.

## Объём (v1)

- Только город Кременчук (не вся область). Если схема окажется рабочей,
  дальше её масштабируют на остальную область — архитектура не должна этому
  мешать, но ничего сверх Кременчука сейчас не реализуется.
- Раскраска — по каждому дому индивидуально (не по улицам целиком). Это
  осознанный выбор: детализация важна, потому что соседние дома могут быть в
  разных очередях.

## Входные данные

Список адресов Кременчука с привязкой к подочереди. Точный формат уточняется
отдельно (может быть txt/JSON/CSV — автор проекта ещё дорабатывает черновик
вручную). Ожидаемая логическая структура одной записи:

```
{ "street": "вул. Жовтнева", "house": "12", "queue": "1.1" }
```

Диапазоны домов ("3-209") в исходнике уже должны быть развёрнуты в отдельные
записи на этапе подготовки списка — дальнейший пайплайн работает с готовыми
домами, не с диапазонами.

## Технологии

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | Vite + TypeScript | Лёгкий, быстрый dev-сервер, без лишнего фреймворка |
| Карта/движок | **MapLibre GL JS** (не Leaflet, не Google Maps) | Единственный из рассмотренных вариантов, где наклон (`pitch`) и объёмные здания (`fill-extrusion`) работают в любом городе — геометрия наша собственная, не зависит от того, включил ли провайдер 3D-рендер именно для Кременчука (у Google это выборочно, в основном крупные города) |
| Базовый фон карты | Векторные тайлы, бесплатный тир MapTiler или Stadia Maps (нужен API-ключ провайдера, не Google) | Нейтральный серый фон — улицы, парки, подписи, без собственных зданий в ярких цветах |
| Слой домов (наша подсветка) | Отдельный `fill-extrusion`-слой из `houses.geojson` (полигоны), поверх базового фона | Это и есть "маска/фильтр поверх карты" — подсвечены только дома из списка, весь остальной город остаётся нейтральным |
| Контуры зданий | OpenStreetMap (Overpass API), разовая выгрузка | Проверено вживую на реальных данных Кременчука (см. ниже) — покрытие достаточное |
| Геокодинг адресов (разовый) | Google Geocoding API | Точнее, чем бесплатный Nominatim, для привязки адреса к точке — используется только как промежуточный шаг для point-in-polygon, не как источник контуров |
| Пространственный join (точка → полигон здания) | `@turf/turf` (`booleanPointInPolygon`) в офлайн-скрипте подготовки данных | Нужно сопоставить геокодированную точку дома с конкретным контуром здания из OSM |
| Хостинг | Любой статический (Netlify / Vercel / Cloudflare Pages / GitHub Pages) | Сайт — чистая статика + fetch, бэкенд не нужен |

### Проверка покрытия зданий в OSM (сделано заранее, не домысел)

Живой запрос к Overpass API по границам Кременчука (24.11.2026):

- Всего контуров зданий в городе: **18 750**.
- Из них с готовым тегом адреса (`addr:housenumber`) прямо на контуре: **4 328** (~23%) — для них сопоставление с нашим списком адресов тривиальное, без геокодинга.
- Отдельные адресные точки без своего контура: **796** — второстепенный источник.
- Остальные ~77% контуров — без адреса, но сама геометрия здания в OSM почти
  везде присутствует: город замаплен плотно, значит геокодированная точка
  адреса в большинстве случаев попадёт внутрь какого-то реального контура
  здания даже без прямого тега.

Вывод: план "красим реальные контуры зданий" для Кременчука реалистичен.
Остаточный риск — отдельные дома (особенно частный сектор на окраинах) могут
не иметь контура в OSM вообще; см. "Фоллбэк" ниже.

### Фоллбэк для домов без контура в OSM

Если для адреса из списка:
1. не нашлось здания с совпадающим тегом адреса, **и**
2. геокодированная точка не попала ни в один контур здания поблизости (порог — например, 30-40 метров),

— такой дом в v1 рисуется простым цветным кружком (MapLibre `circle`-слой) в
этой точке, а не объёмным зданием. Это не должно блокировать запуск: лучше
показать неидеальный кружок, чем молча потерять дом из списка.

### Высота зданий

В OSM почти нет данных о реальной этажности/высоте по Кременчуку, поэтому
полигоны выдавливаются на условную фиксированную высоту (не настоящую) —
визуально это ближе к референсу (стилизованные одинаковые объёмные блоки), чем
попытка тянуть неполные данные о высоте.

## Пайплайн подготовки данных (разовый, офлайн — не часть рантайма сайта)

Скрипт(ы) в `scripts/` на Node.js/TypeScript, запускаются вручную при
подготовке/обновлении списка домов, не на каждой загрузке сайта:

1. **Геокодинг** — по списку адресов дергаем Google Geocoding API
   (`"{street}, {house}, Кременчук, Полтавська область, Україна"`), кэшируем
   результат по исходной строке адреса в `geocode-cache.json`, чтобы не
   платить за повтор. Сохраняем также `precision` (`ROOFTOP` /
   `RANGE_INTERPOLATED` / `GEOMETRIC_CENTER` / `APPROXIMATE`).
2. **Выгрузка контуров зданий Кременчука из Overpass** — разово, кэшируется
   локально (`kremenchuk_buildings.geojson`), не дергается повторно без
   необходимости (публичный Overpass сам просит не злоупотреблять).
3. **Сопоставление адрес → полигон здания**:
   - Сначала пробуем прямое совпадение по тегам `addr:street` +
     `addr:housenumber` на контуре здания.
   - Если тега нет — point-in-polygon (`@turf/turf`) геокодированной точки
     против контуров зданий поблизости.
   - Если ни то, ни другое не сработало — адрес уходит в фоллбэк-список
     (точка/кружок вместо полигона) и отдельно пишется в
     `geocode-failures.json` / `unmatched-buildings.json` для ручной проверки.
4. **Итоговый файл** `public/houses.geojson` — `FeatureCollection`, смесь
   `Polygon` (сопоставленные здания) и `Point` (фоллбэк) фич:

```json
{
  "type": "Feature",
  "geometry": { "type": "Polygon", "coordinates": [[...]] },
  "properties": {
    "address": "вул. Жовтнева, 12",
    "queue": "1.1",
    "match": "osm_addr_tag"   // "osm_addr_tag" | "point_in_polygon" | "fallback_point"
  }
}
```

## Контракт live-статуса (отдаёт бот, не этот проект)

Бот должен будет публиковать публичный read-only эндпоинт (реализуется позже,
в проекте бота, не здесь):

```
GET https://<bot-host>/status.json
Access-Control-Allow-Origin: *

{
  "updated_at": "23.11.2026 14:32",
  "queues": {
    "1.1": "on",      // "on" | "off" | "switching"
    "1.2": "off",
    ...
    "6.2": "on"
  },
  "schedule": {        // необязательное поле, см. "Таймлайн по суткам" ниже
    "1.1": [{"start": "01:00", "end": "04:30"}, ...],
    ...
    "6.2": [...]
  }
}
```

`schedule` — это тот же формат, что уже лежит во внутреннем `state.json` бота
(`parsed["schedule"]`) — отдаётся как есть, без трансформаций. Без этого поля
карта просто не показывает таймлайн-повзунок, вся остальная функциональность
(live-статус, подсветка очереди) не зависит от его наличия.

Сайт карты поллит `status.json` каждые 30–60 секунд и перекрашивает полигоны/
точки без перезагрузки страницы (меняем `fill-extrusion-color`/`circle-color`
через data-driven expression или `setFeatureState`, не пересобираем весь слой).
Если эндпоинт недоступен — последний известный статус остаётся на карте,
полигоны не должны пропадать/сереть молча; стоит показать маленький индикатор
"данные устарели" с таймстампом последнего успешного обновления.

## Таймлайн по суткам (вертикальный повзунок)

Поскольку бот и так знает весь дневной график (не только "сейчас"), карта
даёт повзунок 00:00–24:00: вместо live-статуса дома перекрашиваются в тот
статус, который был/будет у каждой подочереди на выбранную минуту суток, по
её `schedule`. Логика переноса минут в статус — `src/timeline.ts`
(`stateAtMinutes`) — зеркалит то же "мягкое" 30-минутное окно
переключения, что и в текстовых сообщениях бота (`SWITCH_WINDOW_MINUTES` в
`formatter.py`): первые/последние 30 минут интервала — "switching", остальное
внутри интервала — "off", вне интервалов — "on".

Кнопка "Live" возвращает карту к обычному опросу `status.json` вместо
зафиксированной минуты. Интерфейс: вертикальный `<input type="range">`,
повёрнутый через CSS (`rotate(-90deg)`) — верх дорожки = 00:00, низ = 24:00;
рядом — деления 00/06/12/18/24, чтобы было видно, что именно измеряет шкала.

## Цветовая схема

Совпадает с тем, что бот уже рисует на своих картинках графика — визуальная
согласованность между ботом и картой:

| Статус | RGB | HEX |
|---|---|---|
| Є світло (on) | 123, 198, 126 | `#7BC67E` |
| Немає світла (off) | 217, 83, 79 | `#D9534F` |
| Перемикання (switching) | 245, 194, 66 | `#F5C242` |

## UI-требования

- Попап по клику/тапу на здание/точку: адрес, номер подочереди, текущий
  статус, время последнего обновления статуса.
- Мобильная адаптация (телефон — основной сценарий просмотра).
- Без авторизации, без личного кабинета — чисто читающая публичная страница.
- Сетка 6×2 цветных кнопок (1.1–6.2), каждая в цвете своего текущего статуса —
  одновременно легенда и переключатель подсветки одной очереди (клик —
  притушить остальные). Кнопка "ALL" (на всю ширину сетки) сбрасывает выбор.
- Переключатель вида: "игровой" (наклон, `pitch` ~45-60°) / "обычный" (вид
  сверху, `pitch: 0`) — кнопка в углу экрана, анимированный переход через
  `map.easeTo({ pitch, bearing })`. Один и тот же слой домов корректно
  отображается в обоих режимах, доп. логики не требует.

## Явно вне рамок (не делать)

- Парсинг исходного PDF — делается вручную отдельно.
- Реальная этажность/высота зданий — используется условная фиксированная
  высота, не фактическая.
- Вся область, кроме Кременчука — следующий этап, после проверки на одном
  городе.
- Любые изменения в репозитории бота (`mazambik_parser_bot`) — отдельная
  сессия/проект, этот файл только описывает контракт (`status.json`), который
  бот должен будет реализовать со своей стороны.

## Разработка без API-ключей (можно начинать сразу)

Google Geocoding API и ключ тайлового провайдера (MapTiler/Stadia) нужны для
финального качества, но не блокируют старт разработки. Пока их нет —
использовать бесплатные заменители без ключей/регистрации:

- Геокодинг на этапе разработки — **Nominatim** (OSM) вместо Google; менее
  точен для домов, но достаточен, чтобы проверить весь пайплайн целиком.
  Переключить на Google — последний шаг, перед финальным "боевым" прогоном.
- Базовая карта — **OpenFreeMap** (готовые векторные тайлы, без ключа) или
  обычные растровые тайлы OSM как временная заглушка, вместо MapTiler/Stadia.
- Контуры зданий — Overpass API ключа не требует вообще, уже проверено вживую.
- Live-статус очередей — пока бот не отдаёт `status.json`, подставить
  захардкоженный тестовый JSON с теми же 12 ключами подочередей, чтобы
  отладить перекраску независимо от готовности бота.
